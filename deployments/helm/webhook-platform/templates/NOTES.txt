{{ .Chart.Name }} {{ .Chart.Version }} installed as release "{{ .Release.Name }}" in namespace "{{ .Release.Namespace }}".

Containers are disposable. Customer data is not. This chart installed six
stateless workloads and NO database - delete every pod, reinstall against the
same PostgreSQL, and every event, delivery and attempt is still there.

────────────────────────────────────────────────────────────────────────────
THE SIX-STEP INSTALL (ARCHITECTURE.md 38)
────────────────────────────────────────────────────────────────────────────

1. PROVISION POSTGRESQL - external, yours, backed up by you.
   RDS/Aurora, Cloud SQL, Azure Database, Neon, Supabase or self-managed.
   Production topology is  app -> PgBouncer -> PostgreSQL.

2. PROVIDE DATABASE_URL
     --set externalDatabase.url='postgresql://user:pass@pgbouncer:6432/webhook_platform?schema=public&sslmode=require'
     --set externalDatabase.directUrl='postgresql://user:pass@db:5432/webhook_platform?schema=public&sslmode=require'
   directUrl must BYPASS the pooler - transaction pooling breaks Prisma's DDL.
   The install you just ran could not have succeeded without step 2:
   values.schema.json requires it.

3. OPTIONALLY PROVIDE REDIS
     --set externalRedis.url='rediss://redis:6379/0'
   Cache and coordination only. Wipe it and you lose throughput, not data.

4. CONFIGURE SECRETS - there are no defaults, ever (ADR-0006).
     kubectl -n {{ .Release.Namespace }} create secret generic webhook-secrets \
       --from-literal=JWT_SECRET="$(openssl rand -base64 48)" \
       --from-literal=SESSION_SECRET="$(openssl rand -base64 48)" \
       --from-literal=ENCRYPTION_KEY="$(openssl rand -base64 32)"
     helm upgrade ... --set secrets.existingSecret=webhook-secrets
   ENCRYPTION_KEY must decode to exactly 32 bytes. Rotating it without
   re-encrypting endpoint secrets makes every stored secret unreadable.

5. RUN MIGRATIONS - explicit, never on application start (ARCHITECTURE.md 41).
   The chart does NOT migrate for you and there is no pre-upgrade hook, so no
   config tweak can ever change your schema as a side effect.

     helm upgrade --install {{ .Release.Name }} . -n {{ .Release.Namespace }} \
       --set migrations.enabled=true --reuse-values

     kubectl -n {{ .Release.Namespace }} wait --for=condition=complete --timeout=10m \
       job/{{ include "webhook-platform.fullname" . }}-migrate-{{ .Release.Revision }}

   Then set migrations.enabled=false again so the job is not part of the
   steady-state release.

6. DEPLOY / VERIFY

     kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ include "webhook-platform.fullname" . }}-control-api
     kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}

   Ingress is disabled. Reach the dashboard locally with:
     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "webhook-platform.fullname" . }}-dashboard 8088:8080
   Enable it with --set ingress.enabled=true --set ingress.appHost=... --set ingress.ingestHost=...
{{- else }}

   Dashboard + control API : https://{{ .Values.ingress.appHost }}
   Event ingest            : https://{{ .Values.ingress.ingestHost }}
{{- end }}

   Create the first owner explicitly - there is no default account (ADR-0006).

   bootstrap.js reads BOOTSTRAP_EMAIL, BOOTSTRAP_PASSWORD and BOOTSTRAP_ORG from
   its environment and exits if any is missing, so `kubectl exec` on its own
   cannot work. Do NOT pass them with `kubectl exec -- env BOOTSTRAP_PASSWORD=...`
   either: that puts the owner password in your shell history, in the API
   server's audit log, and in anything scraping kubectl arguments.

   Put them in a Secret and run ONE Job that sources them, then delete both:

     kubectl -n {{ .Release.Namespace }} create secret generic webhook-bootstrap \
       --from-literal=BOOTSTRAP_EMAIL='owner@example.com' \
       --from-literal=BOOTSTRAP_ORG='Acme' \
       --from-literal=BOOTSTRAP_PASSWORD="$(openssl rand -base64 24)"

     kubectl -n {{ .Release.Namespace }} create -f - <<'EOF'
     apiVersion: batch/v1
     kind: Job
     metadata:
       name: webhook-bootstrap
     spec:
       backoffLimit: 0
       ttlSecondsAfterFinished: 3600
       template:
         spec:
           restartPolicy: Never
           automountServiceAccountToken: false
           securityContext:
             runAsNonRoot: true
             runAsUser: 1000
             seccompProfile: { type: RuntimeDefault }
           containers:
             - name: bootstrap
               image: {{ include "webhook-platform.image" (dict "ctx" . "image" .Values.controlApi.image "defaultTag" .Chart.AppVersion) }}
               command: ["node", "dist/cli/bootstrap.js"]
               envFrom:
                 - configMapRef: { name: {{ include "webhook-platform.fullname" . }}-config }
                 - secretRef:    { name: {{ include "webhook-platform.fullname" . }}-secrets }
{{- with .Values.secrets.existingSecret }}
                 - secretRef:    { name: {{ . }} }
{{- end }}
                 - secretRef:    { name: webhook-bootstrap }
               securityContext:
                 allowPrivilegeEscalation: false
                 readOnlyRootFilesystem: true
                 capabilities: { drop: ["ALL"] }
     EOF

     kubectl -n {{ .Release.Namespace }} wait --for=condition=complete --timeout=5m job/webhook-bootstrap
     kubectl -n {{ .Release.Namespace }} logs job/webhook-bootstrap

   Then clean up - the password Secret has no reason to outlive the Job:

     kubectl -n {{ .Release.Namespace }} delete job/webhook-bootstrap secret/webhook-bootstrap

   Hand the password to the owner out of band and have them change it.

────────────────────────────────────────────────────────────────────────────
SCALING
────────────────────────────────────────────────────────────────────────────
The throughput dial is workers, not the control plane:
  --set dataPlane.worker.autoscaling.maxReplicas=16 \
  --set externalDatabase.maxConnections=10

maxReplicas is a DATABASE ceiling, not a CPU one. Each worker pod opens
externalDatabase.maxConnections ({{ .Values.externalDatabase.maxConnections }}) and EXITS at startup if it
cannot get them - so a ceiling your pooler cannot serve does not give you
throughput, it gives you CrashLoopBackOff at the moment traffic spiked.

Current ceiling: ({{ .Values.dataPlane.worker.autoscaling.maxReplicas }} workers + {{ .Values.dataPlane.ingest.replicaCount }} ingest + {{ .Values.dataPlane.router.replicaCount }} router + {{ .Values.dataPlane.scheduler.replicaCount }} scheduler)
  x {{ .Values.externalDatabase.maxConnections }} connections, plus the control API's Prisma pool.
Check that against max_connections and PgBouncer's default_pool_size BEFORE
raising either number.
