# Expected schema drift — the ONLY differences `prisma migrate diff` may report
# between apps/control-api/prisma/migrations and apps/control-api/prisma/schema.prisma.
#
# READ THIS BEFORE YOU "FIX" A RED schema-drift JOB.
#
# The migration 20260906010000_review_fixes contains three indexes that Prisma's
# datamodel language CANNOT express. Both that migration's header and
# schema.prisma say so in the file. `prisma migrate diff` compares the migration
# history against the datamodel, so it reports these three as drift BY
# CONSTRUCTION, forever. That is expected. It is not a mistake, and it is not
# something `prisma migrate dev` should be asked to reconcile.
#
# DO NOT RUN `prisma migrate dev` TO MAKE THIS GREEN. It will generate a
# migration that DROPS deliveries_event_endpoint_original_key. That index is the
# ON CONFLICT arbiter the router names when it materialises fan-out. Without it
# a router that inserted its delivery rows and then died before marking the
# outbox row processed is re-run on restart — and every subscriber receives
# every event a second time. Dropping it silently converts a crash into
# duplicate deliveries for every customer.
#
# What to do instead:
#   - Adding a NEW hand-written index Prisma cannot express? Add its name here,
#     with a comment saying why it cannot live in schema.prisma.
#   - Seeing any OTHER identifier in the CI failure output? That is real drift.
#     schema.prisma and the migrations genuinely disagree; write a migration.
#
# One index name per line. Blank lines and #-comments are ignored.

# Partial unique index (WHERE replay_of_delivery_id IS NULL). Prisma has no
# partial-index syntax. This is the fan-out idempotency arbiter — see above.
deliveries_event_endpoint_original_key

# NULLS NOT DISTINCT (PostgreSQL 15+). Prisma always emits NULLS DISTINCT, under
# which the scope-wide policy row (resource_id IS NULL) never matched its own
# upsert and was INSERTed again on every write.
rate_limit_policies_project_id_scope_resource_id_key

# NULLS NOT DISTINCT, same reason: the org-wide usage row (project_id IS NULL)
# duplicated instead of accumulating.
usage_records_organization_id_project_id_metric_period_star_key

# ---------------------------------------------------------------------------
# Added by 20260907000000_handoff_schema_requests. All four are PARTIAL indexes
# (they carry a WHERE clause); Prisma has no partial-index syntax, so all four
# are drift by construction, forever.
#
# NOTE FOR WHOEVER MAINTAINS THE CI JOB: that migration also adds twelve CHECK
# constraints (nine on retry_policies, three on rate_limit_policies). They are
# deliberately NOT listed here. Prisma's datamodel has no concept of a CHECK
# constraint, so `migrate diff` does not report them - and the second CI step
# looks every line in this file up in pg_indexes, where a constraint name will
# never appear. If a future Prisma release starts emitting DROP CONSTRAINT for
# them, this file needs a SECOND list and the job needs a second loop; do not
# paste constraint names into this one.
# ---------------------------------------------------------------------------

# Partial unique index (WHERE is_default). "At most one default retry policy per
# project" was held only inside a SERIALIZABLE transaction in the service. A
# second default is not a visible error - it is a project where which retry
# policy an endpoint gets depends on row order.
retry_policies_one_default_per_project

# Partial index over the delivery ready set, tenant-fair claim
# (WHERE status IN ('pending','scheduled','queued','retrying','processing')).
# 'processing' is in the predicate ON PURPOSE: a leased row IS 'processing', and
# the claim reclaims expired leases. Narrow the predicate and a dead worker's
# deliveries fall outside the index - stuck in 'processing' forever, never
# retried, never exhausted, findable only by sequential scan.
deliveries_ready_idx

# Same ready set, leading with (next_attempt_at, created_at) instead of the
# tenant pair, because CLAIM_STRATEGY=fifo - the SHIPPING DEFAULT - orders
# globally and cannot use an index that leads with organization_id/project_id.
deliveries_ready_fifo_idx

# Partial index over the outbox ready set (WHERE status IN ('pending',
# 'processing')). Covers both the router's ORDER BY (available_at, created_at)
# claim and its MIN(available_at) lag gauge; the Prisma-managed
# (status, available_at) index covers neither without a sort or a full scan.
# An outbox row that is never claimed is an event that returned 202 and will
# never be delivered.
event_outbox_ready_idx
